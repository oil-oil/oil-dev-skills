# 五维代码审查标准、独立审查提示词与严进常删细则

本文配合 `oil-code-review` 使用，聚焦真正影响产品交付质量与长期可维护性的核心问题。

## 1. 五维审查判定细则

### 维度一：业务闭环、正式产物安全与测试质量
- **业务与打包双闭环**：不仅看开发态单测绿不绿，还要看真实用户链路通不通——特别是资源路径、环境变量、条件编译宏在正式构建/独立安装包下是否会失效崩溃。
- **测试有效且无副作用**：
  - 拦住“假测试”：把内部依赖全 mock 掉只测假返回值、全文无实质业务断言、或硬写长 `sleep` 拖慢后续每次跑测试的速度。
  - 拦住“坏副作用”：桌面/客户端测试不得弹窗抢走用户前台焦点、不得触发系统权限授权框、不得直接读写生产全局配置（如默认全局偏好域或用户真实工程目录），不得调用真实外部服务或生产数据库。

### 维度二：组件化、函数化与既有基建复用
- **先看现成基建**：检查新写的弹窗、表单控件、格式化工具、时间换算或样式令牌，仓库公共组件层或核心共享模块里是不是早就有了；能直接复用的绝不允许另起炉灶重写一套。
- **职责拆分干净**：纯计算逻辑与界面视图分离，单文件持续膨胀到四五百行以上且混杂多项职责时，指出清晰的组件或函数拆分边界。

### 维度三：冗余代码与高维护算法排查
- **砍掉冗余**：删除无人调用的残留函数、永远走不到的分支，以及对内部已确定类型的数据做层层套娃式的冗余防御。
- **拒绝炫技式复杂算法**：能用清晰的线性遍历、标准库或简单表驱动解决的问题，如果写成了状态交错、半年后没人敢动的复杂自研算法，直接要求化繁为简。

### 维度四：错误代码扫描
- 重点核查：强制解包/越界崩溃、并发读写竞态、异步任务在视图销毁或用户取消后未中止、空 `catch` 静默吞掉故障、多语言文案只改了一种语言而漏掉配对语言、删除文件或符号后仍有残留引用。
- 明显的性能问题也在这里报：主线程或请求路径上的阻塞 I/O、循环里重复查询数据库或网络、一次性把大文件读进内存。
- 只报读过上下文确认成立的真问题，每条注明精确 `文件路径:行号`、触发条件与实际影响。

### 维度五：安全与兼容
- **安全**：
  - 外部输入（请求参数、文件内容、命令行参数、环境变量）是否未经处理就拼进 SQL、shell 命令、文件路径或 HTML，导致注入、路径穿越或 XSS。
  - 鉴权与权限检查是否缺失、只在前端做、或能被换个参数绕过。
  - 密钥、令牌、个人数据是否写进代码、日志、报错信息或测试夹具；是否关闭了 TLS 校验或用了不安全的反序列化。
- **数据兼容**：存储格式、数据库结构或缓存键变化时，有没有迁移脚本与回退方案；旧版本写下的数据新代码还能不能读；升级中途失败会不会留下半新半旧的数据。
- **接口兼容**：对外 API、CLI 参数、配置字段、事件名、SDK 公共接口有没有删除或改语义；确需破坏时，方案里是否已声明并给出过渡办法。
- **依赖变更**：新增第三方依赖是否必要（仓库或标准库里有没有现成的）、许可证是否允许、锁文件是否同步、版本是否锁定。

## 2. 独立干净上下文审查提示词（高风险改动使用）

对核心产品逻辑做独立深审时，开启全新只读子 Agent（或经 `oil-delegate` 以 `--role review` 委托，按用户偏好选 Agent 并自动只读），避免顺着写代码时的惯性自圆其说：

```text
请以只读方式对当前代码改动执行严格 Code Review（不要修改任何文件，不要触发全量慢测试或弹窗命令）：

【待审范围与项目规范】
<贴入 review_helper.py 输出的改动文件与行号范围>

【已确认方案的范围】（没有方案时删掉这一段）
- 允许修改：<方案里的路径或通配符>
- 本期不做：<方案划出去的模块或功能>
- 必须复用：<方案点名的组件或函数>

请先阅读仓库根目录下的规范文件（如 AGENTS.md / DESIGN.md / REVIEW.md），再结合改动上下文重点核查以下几项：

0. 方案符合度（有方案时）：是否改了允许范围外的文件、碰了本期不做的部分、漏用了必须复用的组件？
1. 业务闭环与测试真假：核心链路与正式打包运行态是否闭环？新增测试是否有真实断言、无固定长 sleep、且无弹窗或污染全局状态的副作用？
2. 基建复用与模块拆分：是否漏用了仓库现成的公共组件、设计令牌或共享函数？单文件职责拆分是否清晰？
3. 冗余与高维护算法：是否有死代码、多余防御包装，或把简单问题写复杂的难维护算法？
4. 运行期缺陷：并发竞态、取消残留、强解包崩溃、静默吞错、阻塞 I/O、多语言漏改、删除后残留引用等真实错误。
5. 安全与兼容：注入与路径穿越、鉴权缺失或可绕过、密钥与个人数据泄露；数据格式变化有无迁移、旧数据能否读取；对外接口有无未声明的破坏性变更；新增依赖是否必要、锁文件是否同步。

如果改动涉及开发约定里的高风险目录或禁改目录，在【待审范围】里注明。不挑缩进或主观命名琐事。只报你读过代码、确认成立的问题，每条附精确 `file:line`、触发条件与实际影响，按 `阻塞问题（Must Fix）` 与 `重要改进（Should Fix）` 输出，最后给出 `PASS` 或 `NEEDS_CHANGES`。
```

收到独立审查结果后，主 Agent 逐条回读对应代码：确认成立的才进入最终结论或交给执行器修复；读不出依据的标为“待确认”或直接剔除，不把未经核实的问题转手给执行器。

## 3. 审查规则沉淀：单源优先、严进常删

### 放在哪里（避免双源割裂）
- 写代码和审代码都要遵守的通用红线，优先直接记入项目统一的 `AGENTS.md` 或 `DESIGN.md`（或写成仓库自己的静态单测），让执行器写代码时一开始就看到，而不是等写歪了靠另一份文档秋后算账。
- 只有当项目积累的跨模块审查经验较多、放进 `AGENTS.md` 会撑破篇幅时，才单独维护精简的 `REVIEW.md`。

### 严进条件（三条全满足才写入）
1. **真高频**：同类问题在审查或线上至少重复出现过 **2–3 次**（偶发一次的局部失误只修代码，不加规则）。
2. **真通用**：跨多个模块或页面都容易再犯，不是某单个历史文件的特例。
3. **非静态可判**：如果几行静态测试或脚本就能 100% 拦住，直接落地自动检查，不靠文档消耗注意力。

### 常删条件（定期清理瘦身）
复盘时遇到以下条目果断删除：
1. **不算真正的问题**：实际执行中经常误报、逼出啰嗦的过度防御代码。
2. **已被静态测试或构建脚本自动兜底**。
3. **涉及的旧模块或旧方案已经重构移除**。
4. **回看数月从未在其他模块发生过第二次的单点规则**。
