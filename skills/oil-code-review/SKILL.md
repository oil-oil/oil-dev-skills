# oil-code-review

`SKILL_DIR` 指当前 Skill 的绝对目录；`<python>` 指 Python 3.10+（macOS/Linux 通常为 `python3`，Windows 通常为 `py -3`）；`REVIEW_HELPER` 是 `<python> "$SKILL_DIR"/scripts/review_helper.py` 的简写。

## 核心规则

- **只审代码，不审方案**：专门审查实际写出的代码与测试；尚未动工的方案文档转交 `oil-plan`。
- **按风险轻重分级，不搞一刀切重审**：并发与后台任务、数据存储格式与迁移、文件删除等不可逆操作、鉴权/权限/支付等安全敏感逻辑、对外 API 与数据契约、打包发布与升级，以及项目开发约定里标为高风险的目录，走**独立干净上下文深度审查**；纯界面排版、样式微调、文案与辅助脚本走**轻量快速核对**，不浪费多轮独立评审时间。
- **五维聚焦，过滤排版琐事**：不挑缩进、引号或个人命名偏好，集中把关**业务与测试真闭环（含打包态与测试隔离）、现成基建复用、冗余与高维护算法、真实运行期缺陷、安全与兼容**五件事，每条问题附精确 `file:line`。
- **快测亲自核实一次，重测只在合并前跑**：执行器自报“快测通过”不能代替验证，审查时亲自跑一次契约里的局部快测（秒级）；全量重测与正式打包检查不在审查时重复跑，集中在合并回主干前统一跑一次。
- **规则沉淀坚持单源优先、严进常删**：真正高频（`>= 2–3` 次）且跨模块通用的坑，优先沉淀进项目现有的 `AGENTS.md` / `DESIGN.md` 或直接写成静态测试（仅在规则较多时单独维护 `REVIEW.md`）；偶发单点问题绝不写入，经常误报或已被脚本接管的伪问题主动提议移除。

## 先选审查档位

| 档位 | 适用改动 | 执行路径 | 默认停止点 |
| --- | --- | --- | --- |
| **轻量审查** | 纯界面样式、排版间距、普通文案、开发辅助脚本（且没有改到高风险目录） | `REVIEW_HELPER` 看改动块 → 对照 `DESIGN.md` / 组件复用与多语言配对快速核查 | 给出简明审查结论 |
| **独立深审** | 核心产品逻辑、上面列出的高风险类别，或采集结果标出 `[高风险目录]` 的改动 | `REVIEW_HELPER` 采集范围 → 独立干净上下文五维审阅 → 合并前统一跑验收门禁 | 输出分级问题清单与 `PASS / NEEDS_CHANGES` |
| **审查规则瘦身** | 定期清理 `REVIEW.md` 或 `AGENTS.md` 中的过时审查项 | 逐条对照近期真实缺陷频率与自动化覆盖情况，提议移除伪问题或低频窄规则 | 经用户确认后完成精简 |

## 工作流

### 1. 采集真实 Git 改动范围

先运行轻量 diff 采集脚本（支持未提交工作区、暂存区、`--base` 分支对比；工作区已提交干净时会自动回退采集当前特性分支领先 `main` 的提交或最近一次提交）：

```text
# 审查当前工作区改动（若已提交干净则自动识别分支/最近提交）
REVIEW_HELPER --workspace "<项目路径>"

# 对比基准分支（同时包含分支已提交记录与工作区未提交修改）
REVIEW_HELPER --workspace "<项目路径>" --base main

# 有已确认方案时，把方案里允许修改的路径传进去，脚本会列出超出范围的改动
REVIEW_HELPER --workspace "<项目路径>" --base main --allow "src/export/**" --allow "tests/export/*"
```

- 输出提示“已自动改为审查已提交范围”时，先确认这就是用户想审的范围，不对就显式传 `--base`。
- 被删除的文件也会列出（标 `[已删除]`），检查是否还有残留引用。
- 仓库 `AGENTS.md` 有 `oil-dev` 开发约定时，输出会标出 `[高风险目录]` 与 `[禁改目录]`：前者一律走独立深审；后者除非方案明确允许，否则列为阻塞问题。没有开发约定时按上面的默认高风险类别判断。
- 同时读取输出中列出的仓库规范文件（`AGENTS.md`、`DESIGN.md` 以及可选的 `REVIEW.md`），以项目自身红线为准绳。

### 2. 方案符合度（有已确认方案或派发契约时）

先核对三件事，再进入五维审查：

1. **范围**：`[超出方案允许范围]` 里的文件逐个确认是必要改动还是顺手发散；必要的向用户说明，发散的列为阻塞问题。
2. **本期不做**：改动是否碰了方案明确划出去的模块或功能。
3. **必须复用**：方案点名要复用的组件或函数是否真的用上了，有没有另起一套。

### 3. 按五维标准核查真实改动上下文

阅读 [五维代码审查标准与提示词](references/review-playbook.md)，按改动块读取代码上下文。涉及高风险代码时用独立的干净上下文审查：已安装 `oil-delegate` 时用 `--role review` 委托，它会按用户保存的偏好选 Agent 并自动只读；返回 `USE_HOST` 时改用当前 Agent 的全新只读子 Agent，返回 `NEEDS_ROLE_CHOICE` 时问用户一次并按 `oil-delegate` 的说明保存；未安装时直接开启当前 Agent 的全新只读子 Agent。审完确认 `git status` 没有变化。独立审查返回的每条 `Must Fix`，主 Agent 都要回读对应代码确认成立，再交给用户或执行器。

审查缺陷修复时，额外确认修复位置就是坏数据产生的地方，而不是在报错的地方挡住症状。

1. **业务闭环、打包一致性与测试真假**：
   - 核心业务与边界流程是否真跑通？脱离本机开发目录打成正式产物（如独立应用包、生产构建或不同分发渠道条件编译分支）后，资源加载与权限是否依然成立？
   - 新增测试是否有真实业务断言？拦截全靠 mock 自证、塞固定秒数 `sleep` 拖慢回归，或弹窗抢焦点、读写用户真实配置或数据、调用真实外部服务等带副作用的坏测试。
2. **组件化、函数化与既有基建复用**：检查新代码是否漏用了仓库已有的公共组件、设计令牌或共享核心模块，以及大文件是否把视图、状态与底层读写混堆在一起。
3. **冗余代码与高维护算法排查**：清理死分支、废弃辅助函数、层层重复的多余防御，以及把常规问题绕成晦涩状态机的自造算法。
4. **运行期错误与遗漏扫描**：核查空值/强解包崩溃、异步取消与并发竞态、空捕获块静默吞错、主线程或请求路径上的阻塞 I/O，以及多语言资源文件（如中英文文案）漏改一边的问题。
5. **安全与兼容**：外部输入是否直接拼进 SQL、命令、路径或 HTML；鉴权与权限检查有没有缺失或可绕过；密钥、令牌或个人数据有没有写进代码、日志或测试数据；存储格式或数据库结构变化有没有迁移与回退、旧数据还能否读取；对外 API、CLI 参数与配置字段有没有未声明的破坏性变更；新增依赖是否必要、许可证是否合适、锁文件是否同步。

### 4. 输出分级结论与严进常删沉淀

1. 输出结构清晰的审查结论：
   - **阻塞问题（Must Fix）**：业务未闭环、打包崩溃隐患、并发/吞错真实缺陷、安全漏洞、没有迁移的数据格式变更、未声明的对外接口破坏性变更、污染用户环境的测试副作用、超出方案范围或改到禁改目录的改动、只在报错处挡住症状而没有修到根因的缺陷修复。
   - **重要改进（Should Fix）**：重复造轮子未复用公共组件、明显冗余或难维护算法、浪费时间的低价值测试。
   - **最终结论**：`PASS` 或 `NEEDS_CHANGES`。
2. 规则沉淀评估（严进常删）：
   - 仅当某类缺陷在仓库中已重复出现 `>= 2–3` 次且跨模块通用时，向用户提议补充 1 条精炼规则（能写成静态单测或脚本拦住的，优先转交 `oil-govern` 程序化拦截）。
   - 若发现现有 `REVIEW.md` 中的旧条目不算真问题、频繁引起过度防御或模块已重构下线，主动提议删掉。

## 输出与后续衔接

审查默认只读，不未经用户同意直接改写业务代码或规范文档。

| 下游意图 | 衔接动作 |
| --- | --- |
| 将确凿的 `Must Fix` 交回执行器修复 | 用 `oil-delegate` 续接原会话，附精确 `file:line` 问题清单，按契约快规则修完跑关联快测；修完只复审这几条问题及其改动，不重审全部 |
| 同一条 `Must Fix` 修了两轮仍不过 | 停止来回返工，进入 `oil-bug-fix` 的止损步骤 |
| 审查通过，准备合并 | 回到 `oil-plan` 的收尾合并步骤跑合并门禁 |
| 将重复踩坑的硬规则固化为自动检查 | 进入 `oil-govern` 编写项目内静态校验测试或检查脚本 |
