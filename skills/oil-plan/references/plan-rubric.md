# 方案可读性标准与严格派发模板

本文配合 `oil-plan` 使用，提供“写给人看懂”的对照标准、动手前真就绪清单、派发给执行器的快规则任务契约，以及收尾合并清单。

## 1. 什么叫“让人看得懂的方案”

方案首先是帮用户做判断和对齐预期的，不是提前默写代码。即使读者不深入研究框架细节，读完也应当一眼明白**接下来软件具体会怎么变、动哪几块、不碰哪里、出异常怎么办**。

### 三不写
1. **不堆砌实现代码**：除必要的简短接口/JSON 契约外，不贴几十行函数实现代码掩盖业务取舍。
2. **不只甩干巴巴的文件名**：每列一个模块或文件，跟上一句平实的话说明它承担哪一步行为变化。
3. **不用正确的废话充数**：不写“优化相关逻辑”“完善异常处理”“补充相关测试”，直接写具体动作与可观察结果。

### 好方案 vs 写了等于没写的方案

| 维度 | 写了等于没写 | 清晰好懂的写法 |
| --- | --- | --- |
| **外部可见变化** | 重构 `ExportController` 状态机并接入取消令牌。 | 点击导出窗口的“取消”按钮后，后台立即停止编码并删除半成品临时文件，按钮恢复可重新导出状态。 |
| **范围、复用与不做边界** | 修改导出模块与弹窗视图。 | 底部操作栏直接复用现成的公共弹窗组件；修改导出调度器传递中止信号。**本期不做**：不支持暂停后断点续传。 |
| **异常与打包边界** | 妥善处理边界并发与资源加载。 | 若点击取消时最后一帧已落盘完成，保留成片并提示已完成；新增图标资源走打包安全的资源查找封装，不直接裸调仅开发态生效的路径。 |
| **分层验证标准** | 运行单元测试确保通过。 | 执行器收尾跑一次导出模块局部快测；合并主干前统一跑一次端到端导出取消回归与正式打包检查。 |

## 2. 动手前真就绪核对（替代形式化打分）

无需在规格文档里填写凑数的百分比表格，直接用以下四问做实质门禁：

1. **路径与复用都查实了吗？** 方案里提到的现有文件、公共组件、设计令牌和快测命令是否都在工作区亲眼核实过（零脑补路径）？
2. **不做边界锁死了吗？** 容易顺手蔓延的相邻功能是否已明确划入“本期不做”？
3. **高风险边界挑过刺了吗？** 涉及并发与后台任务、数据存储格式与迁移、文件删除等不可逆操作、鉴权/权限/支付等安全敏感逻辑、对外 API 与数据契约、打包发布与升级，或开发约定里标为高风险目录的方案，是否核查过失败恢复、安全与兼容影响以及正式包表现（复杂时可调独立只读模型挑刺）？
4. **用户真理解并拍板了吗？** 是否已把关键取舍用日常语言摊开确认，没有把未决分歧留给写代码的执行器去猜？

以上四条任一条未满足，先查代码或问清用户，不急着派单改代码。

## 3. 审批通过后的严格派发契约（含执行快规则）

把已确认的方案交给外部执行 Agent（如经 `oil-delegate`）落地时，提示词要把实现方向和**测试频率纪律**同时锁死，把时间花在写对代码上，而不是花在反复空跑全量测试上。当前会话自己实现时，同样按下面的快规则执行：

```text
请严格按以下已确认方案实现，不要自行扩展需求或额外发明新抽象：

【目标与外部表现】
<几句话写清改完后软件行为的具体变化>

【指定范围与必须复用的基建】
- 必须直接复用：<列出已核实的公共组件、共享类型或工具函数路径>
- 允许修改 / 新建的文件：<写成路径或通配符并注明职责，如 `src/export/**`：导出调度；审查时会逐个比对>
- 本期明确不做：<列出禁止顺手触碰的模块与相邻逻辑；开发约定里的禁改目录一并写上>

【边界、隔离与打包安全要求】
- <写明空状态、并发时序、兼容回退或正式包资源加载要求>
- 安全与兼容：<权限校验与外部输入处理要求；旧数据如何读取或迁移；哪些对外接口、配置字段必须保持兼容>
- 新增测试必须保持隔离：不得抢占桌面窗口焦点、不得触发系统权限弹窗、不得读写用户真实配置或数据目录、不得调用真实外部服务或生产数据库。

【执行快规则（严格遵守）】
1. 修缺陷：先复现。优先写一个能复现问题的测试，运行它并确认失败，再改代码；修完后同一个测试必须通过。做新功能：动手前不用先空跑一遍基线测试。
2. 编码途中可以随时跑编译、类型检查或 lint 这类秒级检查；不要每改一小处就跑测试，严禁中途触发全量测试或重型打包。
3. 全部代码与对应测试写完后，跑与本次改动直接相关的局部快测：<填入具体局部快测命令；有开发约定时用其中的快测命令并替换 {target}>。失败就修，修完重跑同一条命令，最多 3 轮；仍然失败就停下汇报。不要删除、跳过或放宽测试来让它通过。
4. 如果判断某个失败与本次改动无关，不要为了验证去 stash、reset 或回滚代码；在汇报里写明失败用例和判断理由，由调用方核实。
5. 需要改动“允许修改”以外的文件，或发现现有代码与方案描述严重不符时，停下报告原因，不要自行扩大范围。
6. 不要自行执行 git commit / git push。
7. 完成后用 15 行以内简明汇报：改动文件、核心处理点、实际运行过的测试命令及结果（通过/失败数量）。
```

## 4. 收尾合并清单

审查通过后，按顺序完成：

1. **跑合并门禁**：在待合并分支上跑一次方案“分层验证标准”里列出的全量 / 端到端 / 打包检查。这是整个流程里唯一一次跑重测的地方。
2. **门禁失败先归因**：在主干上跑同一条命令对比。是本次改动引入的，续接原执行会话修复，只发送失败用例与关键日志；主干本来就失败的，如实告诉用户，不顺手修无关问题。
3. **提交与合并**：执行器不提交，由主会话按仓库约定（分支命名、提交信息、PR 流程）提交；用户已有一键发布流程（如 git-ship）时交给它。
4. **多个 Worktree 逐个合入**：按依赖顺序合入，每合入一个就在主干上跑一次相关快测；有冲突时以已确认方案为准解决，拿不准就问用户；全部合入后在主干上再跑一次门禁，确认组合起来仍然成立。
5. **清理 Worktree**：合入后用 `oil-govern` 的 Worktree 盘点确认状态，只移除标记为可清理（已合入且无未提交改动）的那几个；显示“没有独立提交”的 Worktree 先问用户再处理。
6. **处理 L3 规格文档**：实现完成后，把仍然有效的结论（数据格式、模块边界、关键约束）并入架构文档或 `AGENTS.md`；规格本身移入 `docs/archive/` 或删除，不让过时的规格留在常驻 `docs/` 里误导后来者。
