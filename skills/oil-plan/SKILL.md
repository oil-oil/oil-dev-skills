# oil-plan

`REVIEW_HELPER` 指 `oil-code-review` Skill 自带的改动采集脚本 review_helper.py，用法见该 Skill；未安装时用 `git status` 与 `git diff --stat` 对照契约代替。

## 核心规则

- **按复杂度分级，拒绝小事大做**：不给两三行明确修改强塞长篇方案文档；按 `L1 / L2 / L3` 选择最轻量的对齐方式。
- **方案审查就在本阶段闭环**：审方案属于 `oil-plan` 内置动作，不混入 `oil-code-review`（后者只审已写出的代码）。
- **必须写成用户看得懂的话**：读者无需关心底层框架内部写法，读完就能清楚知道“外部表现有什么变化、动哪几块与复用什么现成基建、本期不做什么、异常边界与怎么验收”。拒绝术语黑话、空话套话和大段实现代码堆砌。
- **事实核实 + 分歧清零后才动手**：不搞填表式的虚假百分比打分。动手前只卡两条真红线：① 提到的现有文件路径、可复用组件与测试命令已在仓库真实核对存在；② 影响用户体验或范围边界的关键分歧已向用户问清。
- **修缺陷先复现**：无论哪个级别，修缺陷都先复现问题（能写失败测试就先写，并确认它真的失败），修完以同一个用例转绿作为验收。
- **派发契约锁死方向与测试节奏**：交给外部执行 Agent（如经 `oil-delegate`）或当前会话自己实现时，把方向、必复用组件、允许修改的文件和**测试快规则**一次写死，防止执行方自行发散或每改两行就反复空跑重测试。

## 先按复杂度分级（L1 / L2 / L3）

| 级别 | 适用场景 | 执行方式 | 默认停止点 |
| --- | --- | --- | --- |
| **L1 轻量直达** | 单模块明确修补、改文案、调样式、定位清楚的小缺陷 | 2–3 句话说明改法（缺陷先复现）→ 直接修改或派发 → 跑一次关联局部快测 | 完成修改与快测反馈 |
| **L2 对话方案** | 常规单功能开发、中等重构或存在 1–2 个产品取舍 | 核实代码事实 → 在对话里给出精炼四要素方案与待拍板项 → 用户点头后实现 | 用户确认方案（或继续派发实现） |
| **L3 里程碑规格** | 跨多子系统改造、新数据格式/打包链路或高风险架构变更 | 核实事实 → 按项目既有风格写入 `docs/` 规格文档 → 独立挑刺内审 → 用户确认后分批或按 Worktree 派发 | 规格定稿获批，准备进入派发 |
| **审阅既有方案** | 用户给出一份现成方案，问靠不靠谱或有没有漏点 | 对照工作区真实代码与 `AGENTS.md` / `DESIGN.md` 挑出事实冲突、漏用基建与边界漏洞 | 输出问题清单与修订建议 |

**中途升级**：执行中发现要动高风险模块（并发与后台任务、数据存储格式与迁移、文件删除等不可逆操作、鉴权/权限/支付等安全敏感逻辑、对外 API 与数据契约、打包发布与升级，以及开发约定里标为高风险的目录）、改动超出原定文件，或冒出新的产品取舍时，停下来升级到 `L2 / L3` 重新对齐，不硬着头皮做完。`L1` 改动只要碰到高风险模块，仍交给 `oil-code-review` 把关。

## 工作流

### 1. 代码事实与规范前置核对

1. 检查当前会话是否已掌握目标模块的真实路径、可复用公共组件/共享模块以及项目规定的局部快测命令；若尚不清楚，先按 `oil-explore` 只读查实，严禁凭猜测编造路径。
2. 若仓库存在 `AGENTS.md` 或 `DESIGN.md`，先核对架构分层、设计令牌、测试隔离与打包分发方面的硬约束。
3. 若 `AGENTS.md` 有标题含 `oil-dev` 的开发约定小节：快测与门禁命令直接写进验证标准和契约，禁改目录写进契约的禁改范围，改动涉及高风险目录时按中途升级规则处理并安排审查。没有这一节时按上面的默认高风险清单判断，可建议用 `oil-govern` 补上。

### 2. 用平实语言讲清方案（L2 / L3）

参考 [方案可读性标准与派发模板](references/plan-rubric.md)，围绕四个核心问题写清楚（若落盘到 `docs/`，沿用目标仓库原有的标题风格，不强套固定模板词）：

1. **要解决什么与外部可见变化**：对比改动前后用户看到的操作、界面或输入输出具体变成什么样。
2. **改动范围与现成基建复用**：写明直接复用仓库哪套公共组件、共享类型或函数，改哪几个文件（写成路径或通配符，后面审查时直接拿来比对）、为何新建文件，并明确列出**本期不做**的边界。
3. **关键取舍与异常、安全、兼容、打包边界**：有多种做法时用日常语言说明利弊与推荐项；交代空状态、中途取消，权限校验与外部输入处理，旧数据能否读取与如何迁移、对外接口是否保持兼容，以及脱离开发目录后的正式打包运行边界（如资源加载、权限与条件编译）。
4. **分层验证标准**：区分“执行器改完跑的局部快测命令”与“合并前统一跑一次的全量/端到端/打包门禁”。

### 3. 方案内审与关键问题确认

1. **自检与独立挑刺**：逐一核实方案中引用的文件路径在仓库中真实存在；若是 `L3` 跨模块高风险方案且环境已安装 `oil-delegate`，可让习惯严密防御的独立模型挑一遍并发、状态迁移与打包盲区，把成立的硬风险补进方案。委托时用 `--role critique`：它会按用户保存的偏好选 Agent 并自动只读；返回 `USE_HOST` 时改用当前 Agent 的全新只读子 Agent，返回 `NEEDS_ROLE_CHOICE` 时问用户一次并按 `oil-delegate` 的说明保存。回来后确认 `git status` 没有变化。
2. **向用户确认关键决定**：首次提交 `L2 / L3` 方案时，用几句清晰直白的话点出最核心的做法与 1–2 个待拍板选择题，确认用户真正理解并认可接下来要做的事后再动手。若无未决疑问且用户团队约定低摩擦推进，说明所选默认方案后直接执行。

### 4. 严格契约派发与并行隔离

方案确认后进入实现：

- **先保护工作区**：写模式派发前确认工作区干净（`git status` 无未提交改动），或改在独立 Worktree 中执行。用户自己有未提交改动时，先问清是提交、暂存还是另开 Worktree，不让执行器的改动和用户的混在一起。
- **按契约派发**：按 [严格派发契约与执行快规则](references/plan-rubric.md#3-审批通过后的严格派发契约含执行快规则) 组装提示词，把必复用基建、允许修改的文件、禁改范围和**测试控频纪律**写进契约。经 `oil-delegate` 派发时用 `--role implement`，按用户偏好选执行 Agent；返回 `USE_HOST` 时由当前会话自己实现。当前会话自己实现时同样遵守这份快规则。
- **多任务并行 Worktree 隔离**：若同时推进多条互不依赖的任务，先确认各任务修改的热点文件不重叠，分别放入同级父目录下的独立 Git Worktree（不要把子 Worktree 嵌套建在主仓库目录内），并记下每条任务的分支名与 Worktree 路径，供收尾合并使用；在编译缓存较重的原生工程中，可先用写时复制（如 macOS APFS `cp -cR`）克隆主仓库构建目录以省去冷编译等待。
- **验收执行结果，不只听自报**：先用 `REVIEW_HELPER --allow <契约里允许的路径>` 检查有没有越界改动，再看测试有没有被删除、跳过或弱化，然后亲自跑一次契约里的局部快测（秒级，用来核实结果）；慢测试不在这一步重复跑。执行器说“基线本来就失败”时，在主干上跑同一条命令核实。

### 5. 收尾合并

审查通过（或 `L1` 快测通过）后，按 [收尾合并清单](references/plan-rubric.md#4-收尾合并清单) 完成最后一步：在待合并分支上跑一次合并门禁；门禁失败先判断是不是本次改动引入的；按仓库约定提交合并（执行器不自行提交）；多个 Worktree 按依赖顺序逐个合入，全部合入后再跑一次门禁；最后清理已合入的 Worktree，并处理 `L3` 规格文档的去留。

## 输出与后续衔接

方案阶段输出精炼方案与待拍板问题后停止；派发实现完成后交付修改摘要与局部快测结果；收尾阶段交付门禁结果与合并状态。

| 下游意图 | 衔接动作 |
| --- | --- |
| 对高风险或核心产品代码做独立把关 | 进入 `oil-code-review`，把契约里允许修改的路径一并交给它比对 |
| 写方案时发现某块底层调用链还没摸清 | 先用 `oil-explore` 局部查实代码锚点 |
| 合并后清理并行 Worktree | 进入 `oil-govern` 盘点 Worktree，只清理确认可清理的那几个 |
