# 分支看板

分支看板回答一个问题：**这个仓库现在每条线在哪、安不安全、我该做什么**。它面向不熟悉 Git 术语的用户，所以先给结论，按“要用户做什么”分组，用后果说话，并对每条还没进主干的分支给出建议。

## 1. 采集事实

```text
AUDIT_REPO --workspace "<项目路径>" --scope board --fetch --json
```

- `--fetch` 只更新本机记录的云端状态，不改任何分支和文件。没有网络时去掉它，并在看板顶部写明“云端状态可能不是最新的”。
- 判断“进没进主干”以云端主干（如 `origin/main`）为准；没有云端时用本机主干。
- PR 信息靠 `gh` 只读获取；读不到时 `pr_source` 为 `unavailable`，看板上不写 PR，不要猜。

输出里的关键字段：

| 字段 | 含义 |
| --- | --- |
| `main` | 本机主干比云端多出（`ahead`、`local_only_commits`）或落后（`behind`）多少 |
| `main_worktree` | 主目录停在哪个分支、有没有没提交的改动 |
| `repo_flags` | 仓库级的问题，见第 3 节 |
| `branches` | 本机分支：在哪个工作目录、推没推、进没进主干、PR、`flags`、`group` |
| `remote_only_branches` | 只在云端、本机没有的未合入分支，通常是别的电脑或别的 Agent 在做 |
| `changes` | 未合入分支相对主干的提交（`commits`）和改动文件（`files`、`insertions`、`deletions`） |
| `groups` | 程序给出的分组：`needs_decision`、`in_progress`、`cleanable` |

## 2. 看懂每条分支改了什么，并给出建议

对 `needs_decision` 和 `in_progress` 里的每条分支：

1. 读 `changes.commits` 的提交说明和 `changes.files`。说明不够清楚时，读改动最多的一两个文件：`git diff <base>...<分支> -- <文件>`。
2. 用一句用户听得懂的话写“改了什么”，例如“给调试版加了界面对照导出，新增 77 个文件，主要是测试和导出代码”。不要只复述提交说明。
3. 给出一条建议和理由。可选的建议：
   - **开 PR 合进主干**：改动完整、有测试、和主干没有明显冲突。
   - **继续做**：还没做完，或者正在工作目录里改。
   - **先推到云端保存**：只在本机、还没决定要不要，至少先别丢。
   - **放弃并删除**：主干已经用别的方式做了同样的事，或者落后主干太多、改动已经过时。
   - **先确认是谁在做**：只在云端、最近还有提交、不是当前用户的工作目录。
4. 判断依据写在理由里：主干是否已经有等价改动（搜索相同的函数或文件）、落后主干多少（`behind_base`）、多久没动（`days_idle`）、是否改到开发约定里的高风险目录。
5. 要建议合并或重做时，先试合并看会不会冲突：`git merge-tree --write-tree --name-only <base> <分支>`（Git 2.38 及以上）。它不改动任何分支和工作目录，输出开头列出的就是冲突文件；冲突多时建议基于当前主干重做，而不是硬合。

`cleanable` 里的分支只列名字和对应的 PR，不逐个分析。

推送、合并、删除分支和清理工作目录都要等用户确认后再做。

## 3. 仓库级提醒怎么说

| `repo_flags` | 对用户说 | 建议 |
| --- | --- | --- |
| `main_has_local_commits` | 本机的主干比云端多了几个提交，这些提交没经过 PR。 | 先别推。把这些提交挪到一个新分支上开 PR，再让本机主干回到云端的状态。 |
| `main_behind_remote` | 云端主干有新的合并，本机还没拉。 | 拉取云端主干；新分支从云端主干开。 |
| `main_worktree_not_on_default` | 主目录现在停在某个功能分支上，不在主干上。 | 在主目录里改的东西会进这个分支，不会进主干。确认这是你想要的。 |
| `main_worktree_dirty` | 主目录有若干个没提交的改动。 | 列出几个文件，问用户要不要挪到一个分支上。 |
| `remote_info_stale` | 超过一天没和云端同步，下面的状态可能过期。 | 联网后重新生成。 |

分支级 `flags` 的说法：

| `flags` | 对用户说 |
| --- | --- |
| `local_only` | 只在这台电脑上，云端没有；删掉就找不回来了。 |
| `unpushed_commits` | 有几个提交还没推到云端。 |
| `remote_deleted_unmerged` | 云端的分支已经删了，但改动没进主干。 |
| `closed_pr_unmerged` | PR 已经关闭，改动没进主干。 |
| `stale` | 很久没动，也没有打开的 PR。 |
| `tracks_other_branch` | 它跟踪的不是云端同名分支，推送时会出错或推到别处。 |
| `uncommitted_changes` | 工作目录里有没提交的改动，说明有人正在改。 |
| `merged_but_dirty` | 已经进了主干，但工作目录里还有没提交的改动，清理前要先看这些改动。 |

## 4. 版式

不管用哪种方式呈现，内容和顺序都一样：

1. **顶部一句结论**：主干安不安全。没有仓库级提醒时写“主干：本机和云端一致”，有提醒时写第 3 节的说法，并标成警示。
2. **需要你决定**：每条分支一块，写分支名、在哪（工作目录路径 / 没有工作目录 / 只在云端）、状态（用 `flags` 的说法）、改了什么、建议和理由、可选的下一步。
3. **正在进行**：同样的内容，可以更简短。
4. **已进主干，可以清理**：只写数量和几个分支名，以及“看清单再清理”的入口。

### 能画界面时

宿主能在对话里直接渲染界面（例如可视化组件、内嵌 HTML 或 artifact）时，把看板画出来：

- 顶部结论用一行带状态色的横条：一致用成功色，有提醒用警示色。
- 每条需要决定的分支用一张卡片，边框用警示色；正在进行的用普通卡片；可以清理的折叠成一行标签。
- 每张卡片底部放下一步按钮，例如“开 PR”“推到云端保存”“删除”。宿主支持把按钮点击发回对话时就接上，不支持就省略按钮，改成写明可以怎么回复。
- 颜色只表达状态，不做装饰；深色模式下也要看得清。

不要为了显示看板另写文件或启动本地服务。

### 不能画界面时

用 Markdown 输出，结构如下：

```markdown
**主干：本机和云端一致**（最新 #83）

### 需要你决定
**`feat/ui-parity-debug-export`** · 没有工作目录 · 11 月 6 日后没动
- 状态：只在这台电脑上，云端没有；删掉就找不回来了。
- 改了什么：给调试版加了界面对照导出，77 个文件，+2902 / -50。
- 建议：先推到云端保存。主干之后没有做同样的事，但它落后主干较多，要合并需要先同步。
- 回复“推上去”或“删掉”。

### 正在进行
（没有）

### 已进主干，可以清理
本机 14 个、云端 44 个，例如 `fix/0.3.38-review`（#76）、`release/0.3.37`（#71）。回复“清理”先看完整清单。
```
