# oil-bug-fix

## 核心规则

- **先复现，再找原因**：没有复现就不下结论，也不宣布修好。
- **诊断期间不改产品代码**：只加复现测试和临时日志；临时日志在交付前全部删掉。
- **修在源头，不挡症状**：在坏数据第一次产生的地方修。根因修好后，不在报错的地方顺手加兜底；确实需要兜底，在汇报里单独提出，由用户决定。
- **先问为什么会写错**：判断这是个例还是普遍问题。普遍问题在全仓排查，一起处理。
- **改常驻规范先问**：新增自动检查、改 `AGENTS.md` 或 `REVIEW.md` 之前，先征得用户同意。
- **重要操作前先独立检查**：修复涉及数据格式或数据库结构、批量删除文件，或要合进主干时，先让一个独立的只读 Agent 回答会影响什么、能不能撤回、有没有漏掉的东西，再请用户确认。

## 先判断归不归这里

用户已经说清原因和改法时（例如“文案写错了，改成某某”），按小修补处理：直接改，跑相关快测，两三句话汇报，不走下面的流程。仓库 `AGENTS.md` 有标题含 `oil-dev` 的开发约定小节时，快测命令和高风险目录以它为准。

## 工作流

### 1. 复现

先写一个能复现问题的测试，运行它，确认它失败，再往下走。写不了测试时，用一条能重复运行的命令或明确的手动步骤代替。

实在复现不了（只在用户机器或线上出现）时，说明依据了哪些日志和代码推演，在汇报里写明把握有多大、修复后靠什么确认。

### 2. 找根因

选最省事的办法，方法细节见 [根因排查方法](references/root-cause-methods.md)：

- **以前是好的**：在好版本和坏版本之间缩小到具体哪一次提交。提交不多时直接读 `git log` 和 `git diff`；提交多时用 `git bisect`，在临时 worktree 里跑，不动当前工作区。
- **有一个错误的值**：从错误的输出往回追，在模块边界加临时日志，找到它第一次变错的地方。
- **有能正常工作的对照**（另一个输入、平台或配置）：同时运行，逐项缩小差异。

同时满足下面两条，才算找到根因：

- 能讲出从触发条件到现象的完整因果链，每一步对得上代码位置；
- 能解释所有观察到的现象，包括为什么以前没出现、为什么只在某些情况下出现。

### 3. 判断个例还是普遍问题

问一句“为什么会写错”：

- **个例**：手滑写错、漏了一个分支。只修这一处。
- **普遍问题**：原因是一种写法或一种误解，例如同一段逻辑复制了几份、某个接口的用法容易用错、某个约定从没写下来。

是普遍问题时，按这种写法在全仓搜索，列出全部命中的位置，逐个确认是否真的有同样的问题。

### 4. 在源头修

1. 在第 2 步找到的位置做最小改动。下面这些不算修复：说不清坏值从哪来，就在报错处加空值判断、try/catch、重试、sleep 或加大超时；只对报告的那个输入写特判；放宽、跳过或删除失败的测试；一次改好几处，说不清是哪一处起的作用。
2. 普遍问题：命中的位置改法相同、不超过 5 处、不在高风险目录时，一起修掉；超出这个范围，先把清单给用户，或交给 `oil-plan` 写方案。
3. 运行第 1 步的测试，确认它通过。普遍问题的其他命中位置各补一个测试，或说明为什么不补。
4. 运行相关模块的快测，删掉全部临时日志。

修复要改到高风险目录、对外接口或数据格式时，先把根因和修法告诉用户，确认后再改。

### 5. 防再犯

- **个例**：第 1 步的回归测试就够了。
- **普遍问题**：在汇报里提议一种防线，等用户确认后再做：
  1. 能用脚本或测试识别这种写法的，写成项目内自动检查（交给 `oil-govern`）。优先选它，检查不会漏。
  2. 识别不了的，在 `AGENTS.md` 已有的规则里加一条审查重点（规则已经很多时放 `REVIEW.md`）。`oil-code-review` 会读这些文件，以后审查会重点看。

审查重点一条一行，写清看什么、为什么，并注明来源，例如：

```markdown
- 把时间戳换成日期时一律指定 UTC，不用本地时区。（来源：每日报表日期差一天的修复）
```

只命中一处的问题不加审查重点。

### 6. 汇报

```markdown
**根因**：一句话说清。
**因果链**：触发条件 → `path:line` → … → 用户看到的现象
**引入时间**：引入问题的提交（查过历史时）
**个例还是普遍问题**：普遍问题时列出排查到的位置和处理结果
**改了什么**：修复位置，以及为什么改在这里
**验证**：修复前失败、修复后通过的测试和命令
**防再犯**：回归测试，以及提议的自动检查或审查重点
**没验证的部分**：例如打包后的环境
```

用户要提交时，提交说明沿用同样的内容，不单独建缺陷文档。

## 止损

出现下面任一情况立刻停下：连续两三个猜测被推翻；修了两轮测试仍然失败；对话里堆满互相矛盾的猜测。

1. 把已确认的事实、已排除的猜测和复现方式整理成一页，向用户说明现状。
2. 已安装 `oil-delegate` 时，用 `--role diagnose` 分别以 `--role-slot 1` 和 `--role-slot 2` 派发两路独立的只读分析：返回 `USE_HOST` 的那一路改由当前 Agent 的全新只读子 Agent 承担；返回 `NEEDS_ROLE_CHOICE` 时问用户一次要哪两个，按 `oil-delegate` 的说明保存。未安装时开两个全新的只读子 Agent。回来后对照两边的结论，并确认 `git status` 没有变化。
3. 两路都给不出干净的解法，而且问题属于非核心的边缘功能时，提议简化交互或砍掉这个功能。

## 输出与后续衔接

| 下游意图 | 衔接动作 |
| --- | --- |
| 修复面大，需要跨模块改动或产品取舍 | 带着根因和排查清单进入 `oil-plan` 写方案 |
| 修复改到高风险目录，或用户要求审查 | 进入 `oil-code-review`，说明这是缺陷修复和根因位置 |
| 用户同意把普遍问题写成自动检查 | 进入 `oil-govern` 编写项目内检查 |
| 修复完成，准备合并 | 按 `oil-plan` 的收尾清单跑合并门禁 |
