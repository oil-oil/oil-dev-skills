# 根因排查方法

找根因时按手上有什么选方法，可以组合使用。每做一次实验，先想好“如果是它，就会看到什么”，一次只改一个变量。

## 1. 以前是好的：缩小到具体提交

先看好版本和坏版本之间有多少提交：

```text
git log --oneline <好的提交>..<坏的提交>
```

提交不多，或者能确定问题出在哪几个文件时，直接读相关改动：

```text
git log --oneline <好的提交>..<坏的提交> -- <相关文件或目录>
git diff <好的提交> <坏的提交> -- <相关文件或目录>
```

提交多、看不出范围时，用 `git bisect` 自动二分。在临时 worktree 里跑，当前分支、工作区和暂存区都不受影响：

```text
git worktree add --detach <临时目录> <坏的提交>
cd <临时目录>
git bisect start <坏的提交> <好的提交>
git bisect run <复现命令>
git bisect reset
cd <原仓库>
git worktree remove --force <临时目录>
```

- 复现测试通常还没提交，旧版本里没有它。开始二分前把它复制进临时目录；用一个新文件名，避免和旧版本里已跟踪的文件冲突，否则二分在切换提交时会失败。
- `git bisect run` 按复现命令的退出码判断：0 表示正常，1–127（125 除外）表示有问题，125 表示这个版本无法测试、跳过。构建失败的版本应返回 125。
- 新建的 worktree 没有依赖和构建缓存。需要安装依赖或联网下载时，先问用户。
- 找到提交后，读它的完整改动，确认因果链，不要只凭提交说明下结论。汇报里写上提交的短哈希和说明。

## 2. 有一个错误的值：往回追

1. 从用户看到的错误输出出发，找到产生它的函数。
2. 沿调用链往上，在每个模块边界加一行临时日志，打印这个值。
3. 找到“上一步还是对的，这一步变错了”的位置。缺陷就在这一步，不在报错的地方。
4. 结束后删掉全部临时日志。

## 3. 有能正常工作的对照：对比差异

同时运行正常的情况和出错的情况，例如另一个输入、另一个平台、另一份配置。把差异逐项换成一致的，直到现象消失；最后换掉的那一项就是触发条件。

输入很大时，逐步删减输入，直到找到仍能触发问题的最小输入。

## 4. 偶发问题的常见来源

偶发问题先找不确定性从哪来，把它固定下来，变成稳定复现：

| 来源 | 固定的办法 |
| --- | --- |
| 时区、当前时间 | 测试里指定时区，或注入固定的时间 |
| 随机数 | 固定随机种子 |
| 并发与时序 | 串行执行，或在关键位置加确定的等待点 |
| 测试之间共享状态（同一个临时文件、全局变量、缓存） | 单独运行出错的测试，再按不同顺序组合运行 |
| 外部服务、网络、文件系统 | 用本地替身或固定的样本数据 |

找到来源后修掉不确定性本身，不用重试、sleep 或加大超时来掩盖。

## 5. 普遍问题的排查

按根因的写法搜索，而不是按报错信息搜索。例如根因是“把时间戳换成日期时没指定时区”，就搜所有把时间戳换成日期的调用，再逐个确认是否指定了时区。

排查结果在汇报里列成清单：位置、是否有同样的问题、怎么处理的。
